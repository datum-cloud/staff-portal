# System Patterns

Detailed engineering guides live in `docs/engineering/` (architecture, pages and routes, components/UI, data and requests, error handling). This file summarises the patterns that matter most when changing code.

## High-level architecture

A single-package React Router v7 full-stack app (SSR) running on Node with a Hono server (`react-router-hono-server`).

- `app/routes.ts` — the authoritative URL tree, using explicit `layout` / `route` / `index` / `prefix` config. URL topology lives here, not spread through code.
- `app/routes/**` — thin route modules (`loader`, `meta`, `handle`, default component) that orchestrate and compose. `index.tsx` for default pages, `layout.tsx` for nested shells; list → create → `:id` detail trees.
- `app/features/**` — domain-specific UI and logic (components, hooks, types, utils, `index.ts` public API) per business area: activity, assistant, billing, contact, dns, fraud, organization, project, quota, service-catalog, user, etc.
- `app/components/**` — domain-agnostic reusable UI (shell pieces, dialogs, tables, badges).
- `app/modules/**` — cross-cutting foundations: auth, axios clients, graphql client, i18n (Lingui), tanstack query, sentry, loki, prometheus, plugins, assistant, billing helpers.
- `app/resources/**` — API access: generated OpenAPI SDKs (`openapi/`), browser API functions (`request/client/apis`), React Query hooks (`request/client/queries`), server wrappers (`request/server`), GraphQL ops (`gql/`), zod schemas (`schemas/`).
- `app/server/**` — Hono entry, middleware (auth, cache, logger, request-context) and routes (`api.ts` internal proxy, `graphql.ts`, `assistant.ts`, `metrics.ts`, `usage.ts`, `cluster.ts`, `platform.ts`, `chainsaw-tests.ts`).

## Key patterns

- **Request layering:** route/page → query hook (`client/queries`) → API function (`client/apis`) → generated SDK → browser axios → `/api/internal/*` → Hono injects bearer token → upstream. Query hooks call only API functions, never the SDK directly. API functions call the SDK, not raw URLs.
- **Query ownership:** a hook lives with the resource whose endpoint it calls (`contact.queries.ts`, `user.queries.ts`, `project.queries.ts`). Feature query modules are only for feature-specific selectors or multi-resource composition.
- **Generated code is never hand-edited:** `app/resources/openapi/**` (via `npm run openapi:generate`) and `app/modules/graphql/generated/**` (via `npm run graphql`).
- **GraphQL:** same tiers as REST plus a hand-authored selection layer; see `app/resources/gql/README.md`.
- **Errors:** typed `AppError` hierarchy in `app/utils/errors/`; `mapApiError` normalises Axios, GraphQL and unknown errors. 4xx errors are `expected` and stay out of Sentry. See `docs/engineering/05-error-handling-and-reporting.md`.
- **Navigation:** toolbar tabs for peer-level hub pages; `SubLayout.SidebarMenu` for resource/workspace detail contexts. Route links come from helpers in `app/utils/config/routes.config.ts`.
- **i18n:** user-facing strings go through Lingui macros; catalogs in `app/modules/i18n/locales/` are generated by `lingui extract` / `compile`.
- **Forms and validation:** `react-hook-form` with zod resolvers; schemas in `app/resources/schemas/`.
- **URL state:** `nuqs` for query-string state.
- **Kubernetes-style lists aren't time-ordered:** `*.miloapis.com` list endpoints return items by name and can't sort. Some resources (e.g. `Email`) have hash names, so a `limit`-capped list is an arbitrary subset. Newest first means walking every page with `continue` (see `listAllEmails` in `email.api.ts`) or an upstream time-ordered query.
- **Generic proxy 500s:** a 500 with code `HTTP_ERROR` and "An unexpected error occurred" means the upstream call failed with no response (e.g. the 32 MB `maxContentLength` cap in `axios.server.ts`, a socket reset). It is not an upstream 500, which would carry the Kubernetes `Status.message`.
- **Abort signals:** list fetchers take React Query's `signal` and pass it to the SDK, so leaving a page cancels in-flight requests (the proxy answers 499) instead of reporting their errors against the next page.

## Component relationships

- Routes depend on features, components, layouts and resources; features depend on components, modules and resources; components depend only on modules and the design system.
- `app/server` depends on `app/modules` (auth, logging, sentry) and is the only place upstream credentials are attached.
- `app/root.tsx` sets up theme, React Query, nuqs, Lingui and the toaster; layouts add auth and the app shell.
